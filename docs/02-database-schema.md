# Database Schema

All tables below include these columns unless noted otherwise (omitted from each entity's field list to avoid repetition):

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Primary key, generated by the application/Prisma, not DB serial |
| `created_at` | timestamptz | Set on insert |
| `updated_at` | timestamptz | Set on insert, bumped on every update |
| `deleted_at` | timestamptz, nullable | Soft delete marker; `NULL` = active |

### RefreshToken
One row per refresh token issued at login or rotation (added in Sprint 1, migration `add_refresh_tokens`). Only a keyed HMAC-SHA256 hash of the token is stored, never the token itself, so a leaked table cannot be replayed as cookies. Tokens that descend from one login share a `family_id`, so presenting a token that was already rotated can revoke the whole session.

| Field | Type | Notes |
|---|---|---|
| `user_id` | FK → User | Indexed |
| `family_id` | UUID | One per login; kept when a token is rotated. Indexed |
| `token_hash` | text | HMAC-SHA256 of the token with `JWT_REFRESH_SECRET`. Unique |
| `expires_at` | timestamptz | Login time plus `REFRESH_TOKEN_TTL` |
| `revoked_at` | timestamptz, nullable | Set on rotation, logout or reuse detection |

## Relationships (Phase 1)

- `User` 1—1 `Employee`
- `User` 1—N `RefreshToken`
- `User` N—N `Role` (via `UserRole`), `Role` N—N `Permission` (via `RolePermission`)
- `Department` 1—N `Employee`, `Department` 1—N `JobPosition`, `Department` 1—N `Department` (self, sub-departments)
- `JobPosition` 1—N `Employee`
- `Employee` 1—N `Employee` (self, via `manager_id`)
- `Employee` 1—N `LeaveRequest`, `Employee` 1—N `LeaveBalance`
- `LeaveType` 1—N `LeaveRequest`, `LeaveType` 1—N `LeaveBalance`

## Indexing

Beyond the unique constraints already listed per-entity (`User.email`, `Employee.employee_code`, `Employee.work_email`, `LeaveBalance (employee_id, leave_type_id, year)`), add indexes on foreign-key and filter columns that Phase 1 queries hit directly:

- `Employee.department_id`, `Employee.job_position_id`, `Employee.manager_id` — used by the `/employees` list filters and by resolving `manager_id` on leave submission.
- `LeaveRequest.employee_id`, `LeaveRequest.status` — the manager approval queue filters by both.
- `UserRole.user_id`, `RolePermission.role_id` — resolved on every authenticated request to build the permission set; must stay fast as the user base grows.

Prisma creates indexes for foreign keys by default; the ones above are called out because they're also queried directly (not just joined), so the default FK index needs to be confirmed sufficient rather than assumed.

## Forward-compatibility notes

- **UUID keys everywhere**: Phase 2 entities (e.g. `AssetAssignment.employee_id`, `PerformanceReview.employee_id`) will all FK into `Employee.id`, which is only safe to assume stable now because it's a UUID, not an auto-increment integer tied to insert order.
- **`Department` and `JobPosition` as standalone tables** (not inlined strings on `Employee`): Recruitment's `JobPosting` will reference the same `Department`/`JobPosition` tables, so org structure is defined once.
- **Soft deletes from day one**: Payroll and Performance records must remain queryable for compliance even if an `Employee` is later marked `terminated` — the soft-delete convention avoids retrofitting this later.
- **`Employee.manager_id` self-FK established in Phase 1**: Performance Management's review-assignment and Onboarding's approval steps in Phase 2 reuse this same hierarchy rather than introducing a second reporting-line concept.
